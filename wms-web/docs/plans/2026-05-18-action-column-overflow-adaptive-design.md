# 操作列自适应收纳设计

## 背景

当前项目已经将列表页操作列统一为 `table-action-column`，并通过 `table-action-column--1` 到 `table-action-column--4` 做宽度分档。这个方案解决了早期页面分散写 `min-width` 的问题，但仍然依赖“按钮数量约等于所需宽度”的假设。

在实际页面中，按钮文案长度、图标、用户缩放比例、浏览器宽度和固定列布局都会影响最终占用空间，因此即使已经按按钮数量分档，仍然会出现操作列显示不全的问题。根因是宽度分档只能估算空间，无法真正适配不同尺寸。

## 目标

- 所有列表页的操作列在不同窗口宽度下都能稳定显示。
- 每行最多完整直出 3 个操作按钮。
- 第 4 个及以后按钮自动收进“更多”下拉菜单。
- 保持当前动作顺序，不改变既有业务优先级。
- 保留危险操作的二次确认能力。
- 降低页面层重复模板，避免每个列表页继续手写多按钮布局。

## 非目标

- 不引入运行时测量文本宽度的复杂逻辑。
- 不做多行换行展示，避免表格行高不稳定。
- 不在本次改造中重构表格查询、分页或表单逻辑。

## 方案

### 通用组件

新增一个通用组件 `TableActionGroup`，负责渲染操作列中的动作集合。

组件职责：

- 接收页面传入的动作配置数组。
- 过滤不可见动作。
- 将前 3 个动作以内联按钮形式展示。
- 将剩余动作收纳到 `更多` 下拉菜单中。
- 对需要确认的动作统一渲染确认弹层。

### 动作模型

页面层不再直接在模板里堆叠多个 `el-button` 和 `el-popconfirm`，而是声明动作配置，例如：

- `label`
- `icon`
- `type`
- `visible`
- `disabled`
- `confirmText`
- `confirmType`
- `onClick`

组件只负责展示和触发，业务条件仍保留在页面层，避免将业务规则转移到通用组件内部。

### 展示规则

- 可见动作数 `<= 3`：全部直接展示，不出现“更多”。
- 可见动作数 `> 3`：前 3 个直接展示，其余动作收进“更多”。
- 下拉中的动作顺序与原始配置顺序一致。
- 危险动作无论在外层还是下拉内，都需要二次确认。

### 列宽策略

保留 `table-action-column` 作为共享类，但不再依赖固定档位宽度来解决溢出。

新的宽度策略：

- 操作列使用统一的自适应最小宽度，优先保证 3 个按钮和一个“更多”触发器的布局空间。
- 单按钮和双按钮页面继续使用共享样式，但不要求继续使用 `table-action-column--N` 档位来表达最大按钮数。
- 测试关注点从“必须有档位类”转为“必须使用共享动作组件”。

### 页面接入范围

本次覆盖所有 `label="操作"` 的列表页，包括系统管理、仓库管理、物品管理和业务单据列表。

对于只有 1 到 2 个操作按钮的页面，也统一接入 `TableActionGroup`，这样后续新增动作时不会再次回到手写模板模式。

## 测试策略

### 回归测试

更新现有操作列测试，校验：

- 所有 `label="操作"` 的 `el-table-column` 都保留 `table-action-column`。
- 所有列表页操作列都使用 `TableActionGroup`。
- 不再要求 `table-action-column--1~4` 档位类。
- 全局样式中保留共享布局样式，并为“更多”触发器预留一致间距。

### 手工抽查

重点检查以下高风险页面：

- `system/user`
- `system/role`
- `system/menu`
- `business/inbound`
- `business/outbound`

这些页面包含 3 个及以上操作按钮，最容易出现收纳逻辑问题。

## 风险与缓解

### 风险 1：下拉菜单中的危险动作缺少确认

缓解：组件内部统一支持确认配置，不允许页面直接绕过。

### 风险 2：页面业务逻辑被错误抽象到组件中

缓解：组件只接收动作配置和回调，不内置任何业务状态判断。

### 风险 3：大范围替换导致漏改页面

缓解：使用测试遍历所有视图文件，确保每个操作列都使用共享组件。

## 预期收益

- 彻底摆脱“按钮数量估算列宽”的脆弱方案。
- 操作列在不同尺寸下都能稳定显示，不再被截断。
- 页面模板更简洁，后续新增动作只需改动作数组。
- 统一交互规则，降低各页面视觉和行为差异。
