# Warehouse Visual 2D Design

**背景**

当前库房、区域、存放柜、库位分别在独立表格页面维护，用户缺少一个能快速理解空间结构的统一浏览入口。已有前端 `konva` 与 `vue-konva` 依赖，但尚未真正落地库房可视化页面；同时 `area/cabinet/bin` 前端查询接口与后端控制器路径不一致，导致无法串起完整布局数据。

**方案选择**

方案一是让前端继续请求一个假定存在的 `/warehouse/visual/**` 聚合接口，由后端一次性返回布局模型，接入成本低但当前后端并不存在这组接口。方案二是前端最小修正现有 `warehouse/area/cabinet/bin` API，并在页面端完成布局推导与联动状态管理。最终采用方案二，因为它不要求新增后端聚合接口，能以最小必要改动打通真实数据，也更符合本轮“只读展示、无拖拽编辑”的边界。

**页面与组件边界**

- `src/views/warehouse/visual/index.vue` 作为独立的正式库房可视化页面，负责库房切换、加载过程、Konva 画布容器、右侧信息摘要与错误恢复入口。
- `src/views/warehouse/visual/visual-layout.ts` 负责将库房、区域、存放柜、库位组装为可渲染的纯数据模型，输出区域框、存放柜块、库位网格以及页面空态/错误态所需的派生信息。
- `src/views/warehouse/visual/visual-state.ts` 负责区域/柜/库位的点击联动规则，保证选中区域、选中存放柜和选中库位上下文一致。
- `src/api/warehouse/{area,cabinet,bin}.ts` 只修正与后端控制器不一致的查询路径，不额外引入新的后端接口契约。

**布局推导规则**

- 区域按 `sortOrder` 升序、再按 `id` 升序稳定排序，横向流式布局，区域卡片宽度根据其下存放柜数量做最小扩展。
- 存放柜按所属区域聚合后按 `sortOrder`、`id` 稳定排序；优先使用后端已有的 `positionX`、`positionY` 参与排序，如果缺失则退化为规则网格布局。
- 存放柜内部库位按 `row`、`col` 形成二维网格，缺少某个坐标时保留空单元，避免因数据缺口造成布局错位。
- 禁用区域、禁用存放柜、禁用库位统一使用弱化配色，但仍保持可点击，以便用户感知空间占位关系。

**联动与反馈**

- 选择库房后按顺序加载区域、柜、库位，首个可见区域默认选中；点击区域时同步收敛右侧“当前区域”的上下文。
- 点击存放柜时保持所属区域选中，并在摘要区展示该柜的行列规模、库位数与状态。
- 点击库位时仅更新库位摘要，不丢失当前库房、区域、存放柜上下文。
- 无区域、无存放柜、无库位分别给出明确空态文案；接口失败或数据装配失败显示错误态卡片与重试按钮，不渲染无解释的空白画布。

**入口方式**

采用独立页面方案，组件路径为 `src/views/warehouse/visual/index.vue`。页面本身可被动态菜单直接指向 `warehouse/visual`，同时在前端静态路由中增加保底入口，避免菜单尚未配置时页面无法访问。

**验证策略**

- 使用 Vitest 为 API 路径兼容、布局推导、联动状态写纯 TypeScript 单测。
- 使用源码断言测试页面是否包含 Konva 画布、空态、错误态和摘要区等关键结构。
- 执行相关单测、全量 `npm test`、`npm run build`，并对新增页面运行 TypeScript 诊断。
