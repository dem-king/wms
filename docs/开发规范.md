# 备品备件库房管理平台 - 开发规范

---

## 一、后端编码规范

### 1.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 包名 | 全小写，点分隔 | `com.wms.system.service` |
| 类名 | 大驼峰（PascalCase） | `SysUserController` |
| 方法名 | 小驼峰（camelCase） | `getUserById` |
| 常量 | 全大写下划线分隔 | `MAX_RETRY_COUNT` |
| 数据库表名 | 小写下划线分隔 | `sys_user` |
| 数据库字段名 | 小写下划线分隔 | `create_time` |
| DTO类 | 以`Dto`结尾 | `InboundOrderDto` |
| VO类 | 以`Vo`结尾 | `ItemDetailVo` |
| Entity类 | 无特殊后缀，对应表名 | `SysUser` |
| Mapper接口 | 以`Mapper`结尾 | `SysUserMapper` |
| Service接口 | 以`Service`结尾 | `SysUserService` |
| Service实现 | 以`ServiceImpl`结尾 | `SysUserServiceImpl` |
| Controller类 | 以`Controller`结尾 | `SysUserController` |
| Converter类 | 以`Converter`结尾 | `ItemConverter` |

### 1.2 分层架构规范

```
Controller → Service → Mapper → DB
   │           │
   │           └── Event Publish（库存同步/预警触发）
   │
   └── @OperLog（操作日志AOP）
   └── @DataScope（数据范围AOP）
   └── @PreAuthorize（权限校验）
```

| 层 | 职责 | 规范 |
|----|------|------|
| Controller | 接口入参校验、路由、调用Service | 仅做参数校验（`@Valid`）和调用转发，**不含业务逻辑** |
| Service | 核心业务逻辑、事务控制 | 事务注解`@Transactional`标注在写方法上，复杂逻辑抽取private方法 |
| Mapper | 数据访问 | 继承MyBatis-Plus `BaseMapper`，复杂查询写XML |
| Domain | 实体/DTO/VO | entity对应表，dto接收入参，vo返回出参，converter做转换 |
| Event | 领域事件 | 业务操作后发布事件（库存同步/标签更新/预警触发），解耦主流程 |

### 1.3 分层调用规则

- Controller仅做参数校验和调用Service，**禁止包含业务逻辑**
- Service处理业务逻辑，事务注解标注在写方法上
- **禁止Controller直接调用Mapper**
- **禁止Service间循环依赖**，公共逻辑抽取到`wms-common`模块

### 1.4 逻辑删除规范

- 所有实体继承`BaseEntity`，MyBatis-Plus全局配置逻辑删除
- 查询自动拼接`del_flag=0`条件
- 删除操作实际执行`UPDATE SET del_flag=1, last_oper_type='d'`

### 1.5 操作日志规范

- 关键业务操作标注`@OperLog`注解
- 注解属性：`module`（模块）、`type`（操作类型）、`desc`（描述）
- AOP切面自动记录操作人、IP、参数、耗时

### 1.6 数据范围规范

- 需要数据隔离的查询方法标注`@DataScope`注解
- AOP切面根据用户角色自动拼接SQL条件

### 1.7 异常处理规范

- 业务异常统一抛出`BizException`，由`GlobalExceptionHandler`捕获
- 禁止在Controller/Service中直接返回错误码，应抛出异常由全局处理器统一响应
- 异常信息应清晰明确，便于前端展示和日志排查

### 1.8 基础实体规范

所有实体继承`BaseEntity`，包含以下公共字段：

| 字段 | 说明 |
|------|------|
| id | 主键（雪花ID） |
| delFlag | 逻辑删除标识（0-正常，1-删除） |
| createTime | 创建时间 |
| updateTime | 更新时间 |
| createBy | 创建人 |
| updateBy | 更新人 |

## 二、前端编码规范

### 2.1 组件规范

- 页面组件使用`<script setup lang="ts">`
- 组件命名大驼峰，文件命名小驼峰或kebab-case
- Props定义使用`defineProps<T>()` + `withDefaults`
- 事件使用`defineEmits<T>()`
- 组件内逻辑抽取为`hooks/`组合式函数，保持组件精简

### 2.2 状态管理规范

- **全局状态（Pinia）**：用户信息、权限菜单、应用配置
- **局部状态**：组件内`ref`/`reactive`
- **禁止**在组件中直接操作`localStorage`，通过工具函数封装

### 2.3 API调用规范

- 所有API调用通过`src/api/`统一管理，按模块分目录
- 使用`request.ts`封装的Axios实例（含拦截器/Token/错误处理）
- 接口函数返回类型明确声明
- API文件命名与后端模块对应

### 2.4 权限控制规范

| 级别 | 实现方式 |
|------|---------|
| 路由级 | 动态路由根据用户菜单权限生成 |
| 按钮级 | 使用`v-permission`指令或`usePermission`钩子 |
| 数据级 | 后端`@DataScope`注解控制 |

### 2.5 目录结构规范

| 目录 | 用途 |
|------|------|
| `src/api/` | API接口定义，按模块分目录 |
| `src/views/` | 页面组件，按模块分目录，每个页面含`index.vue`和`components/` |
| `src/components/` | 全局通用组件 |
| `src/hooks/` | 组合式函数（useTable、useForm、useCrud等） |
| `src/store/` | Pinia状态管理，按模块分文件 |
| `src/utils/` | 工具函数 |
| `src/types/` | 全局TypeScript类型定义 |
| `src/layouts/` | 布局组件 |
| `src/styles/` | 全局样式（SCSS变量/混入/重置） |

### 2.6 样式规范

- 全局样式变量定义在`styles/variables.scss`
- 使用SCSS混入（`styles/mixins.scss`）复用样式片段
- 组件样式使用`<style scoped lang="scss">`，避免全局污染

## 三、API接口规范

### 3.1 接口风格

- **RESTful风格**，模块化路径
- 统一前缀：`/api/v1`
- 认证方式：Bearer Token（JWT）
- Content-Type：`application/json`

### 3.2 统一响应体

```json
{
    "code": 200,
    "msg": "操作成功",
    "data": {}
}
```

| code | 含义 |
|------|------|
| 200 | 成功 |
| 400 | 业务异常 |
| 401 | 未认证 |
| 403 | 无权限 |
| 500 | 系统异常 |

### 3.3 分页请求/响应

**请求：**
```
GET /api/v1/items?page=1&size=20&sort=createTime,desc
```

**响应：**
```json
{
    "code": 200,
    "data": {
        "records": [],
        "total": 100,
        "page": 1,
        "size": 20
    }
}
```

### 3.4 路径命名规范

- 使用小写复数名词表示集合：`/users`、`/items`、`/orders`
- 子资源用嵌套路径：`/categories/{id}/sub`
- 动作用动词后缀：`/orders/{id}/submit`、`/labels/{id}/bind`

### 3.5 HTTP方法语义

| 方法 | 语义 | 幂等 |
|------|------|------|
| GET | 查询 | 是 |
| POST | 新增/执行操作 | 否 |
| PUT | 更新 | 是 |
| DELETE | 删除 | 是 |

## 四、数据库规范

### 4.1 命名规范

| 类型 | 规范 | 示例 |
|------|------|------|
| 表名 | 小写下划线，模块前缀 | `sys_user`、`wms_inbound_order` |
| 字段名 | 小写下划线 | `create_time`、`del_flag` |
| 主键 | `id` | `id` |
| 外键 | 关联表_关联字段 | `warehouse_id`、`item_id` |
| 索引 | `idx_表_字段` | `idx_item_category_id` |
| 唯一索引 | `uk_表_字段` | `uk_user_username` |

### 4.2 公共字段

所有业务表必须包含以下字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | bigint | 主键（雪花ID） |
| del_flag | tinyint | 逻辑删除（0-正常，1-删除） |
| create_time | datetime | 创建时间 |
| update_time | datetime | 更新时间 |
| create_by | varchar | 创建人 |
| update_by | varchar | 更新人 |

### 4.3 设计原则

- 使用逻辑删除，禁止物理删除业务数据
- 金额字段使用`decimal`类型，禁止使用`float`/`double`
- 状态字段使用`tinyint`，配合枚举类使用
- 时间字段使用`datetime`，禁止使用`varchar`存储时间
- 外键关联在逻辑层控制，不建立物理外键约束

## 五、Git规范

### 5.1 分支策略

```
main          ← 生产分支
  └── develop ← 开发主分支
        ├── feature/P1-item-archieve    ← 功能分支
        ├── feature/P2-warehouse-visual
        ├── feature/P3-approval-flow
        ├── fix/stock-sync-bug          ← 修复分支
        └── release/v1.0.0             ← 发布分支
```

| 分支类型 | 命名格式 | 说明 |
|---------|---------|------|
| 主分支 | `main` | 生产代码，仅通过merge release更新 |
| 开发分支 | `develop` | 开发集成，日常开发基础 |
| 功能分支 | `feature/<phase>-<name>` | 如`feature/P1-item-archieve` |
| 修复分支 | `fix/<name>` | 如`fix/stock-sync-bug` |
| 发布分支 | `release/v<version>` | 如`release/v1.0.0` |

### 5.2 Commit规范

```
<type>(<scope>): <subject>
```

**type类型：**

| type | 说明 |
|------|------|
| feat | 新功能 |
| fix | 修复Bug |
| refactor | 重构（非新功能、非修复） |
| docs | 文档变更 |
| style | 代码格式（不影响逻辑） |
| test | 测试相关 |
| chore | 构建/工具变更 |

**scope范围：**

| scope | 说明 |
|-------|------|
| system | 系统管理模块 |
| warehouse | 库房结构模块 |
| item | 物品管理模块 |
| business | 业务单据模块 |
| approval | 审批流程模块 |
| report | 统计报表模块 |
| monitor | 预警监控模块 |

**示例：**
```
feat(business): 新增入库单扫码入库功能
fix(item): 修复库存同步事件未触发问题
refactor(system): 重构权限校验逻辑
```

### 5.3 分支操作规范

- 功能分支从`develop`拉出，完成后通过PR合并回`develop`
- 禁止直接向`main`提交代码
- PR合并前需通过代码审查和CI检查
- 合并后及时删除功能分支

## 六、接口文档规范

- 使用Knife4j（Swagger增强）自动生成API文档
- 每个Controller添加`@Tag`注解（标注模块名）
- 每个接口添加`@Operation`注解（标注接口说明）
- DTO/VO字段添加`@Schema`注解（标注字段含义）
- 接口文档与代码同步维护，禁止文档与实现不一致

## 七、安全规范

### 7.1 认证与授权

- 认证方式：JWT Bearer Token
- Token存储：Redis（支持主动失效/续期）
- 权限模型：RBAC（用户→角色→菜单/权限）
- 数据隔离：`@DataScope`注解控制数据可见范围

### 7.2 安全原则

- 密码使用BCrypt加密存储，禁止明文
- 敏感接口必须添加`@PreAuthorize`权限注解
- 前端Token存储于Cookie/SessionStorage，禁止LocalStorage
- API接口统一通过Nginx反向代理，禁止直接暴露后端端口
- 生产环境必须启用HTTPS
- 禁止在日志中输出敏感信息（密码/Token/身份证号等）
- 禁止在代码中硬编码密钥/密码，使用配置文件或环境变量

## 八、日志规范

### 8.1 后端日志

- 框架：Logback
- 配置文件：`logback-spring.xml`
- 日志分级：ERROR > WARN > INFO > DEBUG
- 生产环境日志级别：INFO
- 开发环境日志级别：DEBUG

### 8.2 业务操作日志

- 关键业务操作标注`@OperLog`注解，由AOP切面自动记录
- 记录内容：操作人、操作时间、IP、模块、操作类型、请求参数、耗时
- 业务操作日志独立存储，支持查询和导出

---

## 九、缓存规范

- 使用Spring Cache抽象 + Redis实现
- 缓存Key命名：`wms:<module>:<business>:<id>`
- 缓存失效：写操作时主动清除相关缓存
- 热点数据：用户权限菜单、字典数据、系统配置
- 禁止缓存大对象，单Key数据不超过1MB

## 十一、代码审查规范

### 11.1 审查要点

- 代码是否符合分层架构规范（Controller不含业务逻辑、Service不含展示逻辑）
- 命名是否规范且语义清晰
- 关键操作是否标注`@OperLog`注解
- 敏感接口是否添加`@PreAuthorize`权限注解
- 数据隔离是否添加`@DataScope`注解
- 事务边界是否正确（写方法加`@Transactional`）
- 异常处理是否规范（抛BizException，由全局处理器捕获）
- 是否存在硬编码敏感信息

### 11.2 实体类字段注释规范

- 实体类（Entity/DTO/VO）的每个字段**必须**添加中文注释，说明字段的业务含义
- 中文注释必须与数据库表字段的中文含义保持一致
- 注解方式优先使用`@Schema`注解（Swagger文档同步），同时字段上方添加JavaDoc注释
- 示例：

```java
public class WmsItem extends BaseEntity {

    /** 物品编码 */
    @Schema(description = "物品编码")
    private String itemCode;

    /** 物品名称 */
    @Schema(description = "物品名称")
    private String itemName;

    /** 规格型号 */
    @Schema(description = "规格型号")
    private String specModel;

    /** 计量单位 */
    @Schema(description = "计量单位")
    private String unit;
}
```

### 11.3 代码注释规范

- 所有编写的代码**必须**添加中文注释，包括但不限于：
  - 类级别：说明类的业务用途和职责
  - 方法级别：说明方法的业务功能、参数含义、返回值含义
  - 关键逻辑：复杂业务逻辑处添加行内注释说明处理意图
  - 分支判断：`if/else`、`switch`等分支处注释说明各分支的业务场景
  - 异常处理：`catch`块注释说明异常的业务含义和处理策略
- 注释使用JavaDoc格式（`/** */`），行内注释使用`//`
- 禁止无意义注释（如`// 赋值`、`// 判断`），注释应说明**为什么**而非**是什么**
- 示例：

```java
/**
 * 入库单服务实现类
 * 处理入库单的创建、审核、完成等业务逻辑
 */
public class InboundOrderServiceImpl implements InboundOrderService {

    /**
     * 创建入库单
     * 校验库房是否存在且启用，生成入库单号，保存入库单及明细
     *
     * @param dto 入库单创建参数，包含库房ID、供应商ID、明细列表
     * @return 创建后的入库单VO
     */
    @Override
    @Transactional(rollbackFor = Exception.class)
    public InboundOrderVo createOrder(InboundOrderDto dto) {
        // 校验库房是否存在且为启用状态
        Warehouse warehouse = warehouseService.getById(dto.getWarehouseId());
        if (warehouse == null || warehouse.getDelFlag() == 1) {
            throw new BizException("库房不存在或已禁用");
        }

        // 生成入库单号：格式为RK + 年月日 + 4位流水号
        String orderNo = generateOrderNo("RK");

        // 状态为待审核时，发布入库单创建事件
        if (OrderStatus.PENDING_REVIEW.equals(dto.getStatus())) {
            eventPublisher.publishEvent(new InboundOrderCreatedEvent(orderNo));
        }

        return converter.toVo(savedOrder);
    }
}
```

### 11.4 审查流程

1. 提交PR并关联任务编号
2. 至少一名团队成员审查通过
3. CI检查全部通过（构建+测试+扫描）
4. 审查通过后合并到目标分支
